## Falhas: saída literal, causa e onde mexer

A causa e o local vêm de leitura do código e de reprodução no projeto de teste. Nada foi consertado.

### 1. vault-guard no modo universal deixa passar Read e Write direto na Central (B1 e C5a)

```
FALHOU vault-guard.mjs    universal: Read direto na raiz central                         saída=0 esperado=2 | 
FALHOU vault-guard.mjs    universal: Write direto no _comum                              saída=0 esperado=2 | 
```

Causa: `raizCentral()` (`.claude/hooks/vault-lib.mjs`) devolve `resolve(HARNESS_VAULT_CENTRAL)`, sem resolver link simbólico. O alvo de Read e Write passa por `targetPath()`, `caminhoRelativo()` e `realDe()` (`hook-io.mjs`), que usa `realpathSync.native`. No macOS, `os.tmpdir()` é `/var/folders/...`, link para `/private/var/folders/...`; os dois caminhos não batem e `dentroDe()` dá falso. Em Linux, onde as provas anteriores rodaram, não há esse link. Reprodução no projeto de teste (pasta `diag-vault/`, apagada logo depois), mesmo evento de Read, só mudando a variável:

```
HARNESS_VAULT_CENTRAL=/var/folders/3h/j_b9vx3d15162t82hnlsnpxm0000gn/T/central-x -> Read saída=0
HARNESS_VAULT_CENTRAL=/private/var/folders/3h/j_b9vx3d15162t82hnlsnpxm0000gn/T/central-x -> Read saída=2
```

Impacto: no Mac, se `HARNESS_VAULT_CENTRAL` apontar para um caminho com link simbólico, Read e Write direto na Central passam. Glob e Bash continuam barrados. Onde mexer: resolver a raiz da Central com o mesmo `realDe()`, em `raizCentral()` ou no `vault-guard`.

### 2. O selftest dos hooks depende do gates.lock real do projeto (C5a)

```
FALHOU git/gates          só documentação (docsOnly), sem código: passa                      saída=1 esperado=0 | gates.lock: o lock espera um projeto com package.json, mas não há nenhum.
FALHOU git/gates          docsOnly mas há código no commit: reprova                          saída=1 esperado=1 | gates.lock: o lock espera um projeto com package.json, mas não há nenhum.
FALHOU git/gates          backend/package.json existe e o lock diz docsOnly: reprova         saída=1 esperado=1 | gates.lock: o que define os gates mudou sem o humano travar de novo:

3 caso(s) de git/gates falharam.

3 caso(s) falharam: os hooks NÃO estão protegendo.
```

Causa: `selftest-git.mjs` (linhas 41 a 43) copia o `.githooks/gates.lock.json` do projeto para o repositório temporário, e os casos das linhas 54 a 61 supõem um lock `docsOnly`. No kit, o lock é `docsOnly: true`; no projeto, depois do `travar-gates` com `package.json`, é `docsOnly: false`. Impacto: num projeto real já travado, `node .claude/hooks/selftest.mjs` nunca sai com zero, e o instalador diz que ele precisa sair com zero. Onde mexer: o selftest cria o próprio lock em vez de copiar o do projeto. Defeito menor junto: o total impresso conta a parte git como um caso só (`selftest.mjs`, linha 23), por isso "3 caso(s)" para cinco linhas FALHOU.

### 6. Codex escreve código sem bloqueio (F1)

Evento observado (`codex exec --json`, sem segredo): `item.completed file_change [{"path":"/Users/joaogabrielaragaodesouza/harness-teste/src/y.ts","kind":"add"}]`. Resposta final do Codex: "A única tentativa não foi bloqueada; `src/y.ts` foi criado com a linha solicitada." Arquivo criado com `export const y = 1;` (sha256 `642703ea05d8`).

Causa principal: o Codex 0.163.0 só roda hook de projeto que tenha confiança gravada, hook por hook (`[hooks.state."<projeto>/.codex/hooks.json:pre_tool_use:0:0"]` com `trusted_hash` em `~/.codex/config.toml`). Não há entrada para `~/harness-teste`, então o `guarda-externa.mjs` não rodou. A confiança no projeto foi dada só em memória (`-c 'projects={ "/Users/joaogabrielaragaodesouza/harness-teste" = { trust_level = "trusted" } }'`), sem gravar nada; ela fez o Codex carregar `.codex/rules` (o F2 mostra), mas não confia no hook. O `codex exec --help` oferece `--dangerously-bypass-hook-trust` ("Run enabled hooks without requiring persisted hook trust for this invocation"), que o classificador do modo auto negou.

Evento bruto enviado ao hook: **não capturado**, porque o hook não rodou. O registro da sessão (`~/.codex/sessions/2026/10/20/rollout-2026-10-20T10-39-34-...jsonl`) mostra que o modelo não chama `apply_patch` direto: chama a ferramenta `exec` (modo código, JavaScript) com:

```
const r = await tools.apply_patch("*** Begin Patch\n*** Add File: src/y.ts\n+export const y = 1;\n*** End Patch");
```

Hipótese a confirmar com o hook confiado: se o hook receber `tool_name: "exec"` com o JavaScript no `tool_input`, (a) o matcher do `.codex/hooks.json` (`Bash|apply_patch|mcp__.*`) não casa com `exec`; (b) mesmo que seja chamado, `normalizar()` trata `exec` como shell (regex `SHELL`) e lê só `command`, `cmd` ou `script`, então o JavaScript fica de fora e nada é conferido. Parte de `normalizar()` a mudar: o ramo de shell precisa reconhecer o `exec` do modo código e extrair as chamadas `tools.apply_patch(...)` (caminhos do patch) e `tools.exec_command({cmd})` (comando).

Ligado a isto: o `doctor` imprime "OK Codex e Antigravity: projeto marcado como confiável nesta máquina" sem conferir nada (`doctor.mjs`, linhas 186 a 191, passa `true` fixo). No Codex, a confiança do projeto e a do hook ficam em `~/.codex/config.toml` e podem ser conferidas.

### 7. OpenCode escreve código sem bloqueio (F4)

Evento bruto da CLI (`opencode run --format json`, ferramenta `write`): `{"path":"/Users/joaogabrielaragaodesouza/harness-teste/src/y.ts","content":"export const y = 1;\n"}`, resultado `Created file successfully: src/y.ts`.

Causa 1, o plugin não carrega. Log do OpenCode (`~/.local/share/opencode/log/opencode.log`, 13:35:33 UTC):

```
level=WARN run=17a6f8be message="failed to load plugin" target=/Users/joaogabrielaragaodesouza/harness-teste/.opencode/plugin/harness-guard.ts ref=err_cccf2083 cause="Cause([Fail(PluginModule.LoadError: Plugin must export a default definition with an id and an effect or setup function. (cause: SchemaError(Missing key\n  at [\"default\"])))])"
```

O `harness-guard.ts` usa a API 1.x (export nomeado que devolve `tool.execute.before`); o OpenCode 2.0.22 exige export default com `id` e `effect` ou `setup`. A falha é só um aviso no log: o OpenCode segue sem a guarda (falha aberta, ao contrário do que o comentário do plugin promete).

Causa 2, mesmo carregado, o plugin deixaria passar. Simulação com o evento exato:

```
guarda com path=/Users/joaogabrielaragaodesouza/harness-teste/src/y.ts: saída=0
src/y.ts está fora do seu escopo. A Infra (OpenCode) escreve só o roteiro de deploy em docs/fluxo/ e a configuração de entrega. Registre o resto no relato e devolva.
guarda com path=src/y.ts: saída=2
```

`normalizar()` passa o `path` absoluto como veio, e `escopo()` pula qualquer caminho que comece com "/" (`if (p.startsWith("/") || ...) continue;`). Parte a mudar: `normalizar()` (ou `escopo()`) deve tornar o caminho relativo à raiz do projeto (o `caminhoRelativo()` de `hook-io.mjs` já faz isso) e tratar caminho fora do projeto como fora do escopo. Observação: o OpenCode 2.x chama a ferramenta de shell de `shell`; a regex `SHELL` da guarda já aceita esse nome, e o OpenCode traduziu `permission.bash` do `opencode.json` para regras de `shell` (`opencode debug config`).
